# Agent Note: GGUF 读取器只解析头部，并把 Node I/O 挡在主入口之外

Status: implemented

[English](2026-08-25-engine-gguf-header-reader.md) | 中文

## Problem

容量估算器（S2）、下载管理器（E3）与模型管理卡片（S1）都需要在任何模型加载之前拿到 GGUF 事实——架构、量化、上下文长度、聊天模板。朴素读取意味着把数 GB 的权重文件载入内存，或为几千字节的头部引入沉重的运行时依赖。

## Decision

`@deepseek-ai/dsh-gguf-metadata` 交付一个零依赖的头部解析器。两个值得记录以防重审的选择：

- **只流式解析头部。** 解析器经 `GgufByteSource` 游标对键值区只走一遍，只物化被捕获的字段并按算术跳过数组载荷；每次读取都对照源自规范的固定上限校验，损坏或恶意构造的头部响亮失败。张量列表内容刻意不读。
- **主入口浏览器安全，文件能力放 node 子路径。** `.` 暴露字节进／元数据出的接口且不含任何 Node 内建模块，客户端消费方与宿主共享同一解析器；`./node` 增加基于滑动窗口的定位文件读取。子路径默认值指向 tsc 产物树（`lib/types/node.js`），符合工作区约束已识别的额外入口模式。

不支持的容器版本（v1）、未知值标签、嵌套数组、超限计数与截断都以 `GgufError` 拒绝；字段缺失在 `GgufMetadata` 中保持可观察。

## Alternatives considered

- **复用现成 npm GGUF 解析器** — 没有在维护的库同时满足 v2/v3、只读头部与跳过语义；此处手写约 200 行即可覆盖，不删除任何自有代码。
- **单入口动态导入 `node:fs`** — 否决：它迫使打包器对内建模块做桩替换，也让意外的仅服务端导入渗入客户端依赖图。
- **返回原始键值映射** — 否决：词表数组使朴素保留无界增长，而今天的消费方需要的不超过所暴露的六个字段。

## Consequences

E3 可以低成本校验下载完整性，S2/S1 无需运行时依赖即获得容量估算输入。上游新增的 `LLAMA_FTYPE_*` 成员扩展标签表；未知值已经按文档降级为 `ftype-N` 渲染而非失败。
