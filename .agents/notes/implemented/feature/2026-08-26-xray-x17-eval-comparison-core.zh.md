# Agent Note：先给已有的运行打分，运行本身的接线随后落地 —— X17 核心先行

Status: implemented

[English](2026-08-26-xray-x17-eval-comparison-core.md) | 中文

## 问题

X17 要求 preset 训练器评估闭环：让候选与基线在基准协议任务上无头对跑，对 PES 与任务通过率打分，并把比较报告作为 `ctx.jobs` 任务发出。判定逻辑是纯数据工作；但执行的一半——在两个 preset 下生成带评分的无头会话——属于真实 API 领域且没有离线预言者。一次落地同时构建两半，要么交付从未被行使的生命周期代码，要么伪造覆盖。

## 决策

在该行天然的分界处拆分；本次落地交付 `dsh-preset-trainer` 中一切可离线测试的部分：

- **评估词汇**（`EvalRun`、`TaskScore`、`EvalThresholds`、`EvalComparison`）：一次运行是在某个 preset 标签下执行完的任务列表，附带镜像 sidecar `post_run_pes.pes` 形状的运行级可选 PES。
- **纯核心**（`summarizeEvalRun`、`compareRuns`）：通过率、PES 差值、逐任务翻转，以及全显式阈值下的判定——基线每个任务都必须被执行（漏跑即响亮失败）、净新增失败（回归减收益）须落在 `allowNewFailures` 内、PES 跌幅须落在 `maxPesDrop` 内。候选多出的任务只报告、不惩罚。同一运行内重复的任务 id 直接抛出：那是损坏的产物，不是可比较的数据。
- **该包的双语 README**（本基线上此前不存在），记录运行形状、判定规则与暂缓事项。

活执行器端口与 `ctx.jobs` 生产者包装刻意延后到 keyed-e2e 后续；README 的已知限制点明了这一点，消费者不会误以为 `compareRuns` 会启动任何东西。

## 已考虑的替代方案

- **现在就用测试中的 mock 运行落地执行器与任务包装**——拒绝：围绕 mock 生产者手搭的任务生命周期只证明管道存在，不证明行为，而且在有人为 e2e 注入密钥之前它将是那段代码唯一的行使方式；被延后的切片保持诚实。
- **复用 `dsh-bench` 的报告解析作为运行来源**——暂时拒绝：sidecar 报告给 sidecar 协议运行打分，不是按 preset 区分的任务列表；把两者混同会把错误的单位烤进契约。`pes?: number` 字段镜像其数值但不引入其形状。
- **净失败规则改为毛回归计数**——拒绝：修好 t3 同时弄坏 t2 的候选在总量上是质量中性的；阈值用于约束损害，不是禁止变动。毛计数仍可在比较字段中看到。

## 后果

X9（基准回归门）与 X18（晋升流）今天就能消费 `compareRuns`，不必重造判定逻辑。评估闭环后续恰好只剩两件事：一个从无头运行产出 `EvalRun` 的执行器端口，以及包装它的任务生产者——它们要喂的打分核心已经冻结并有测试。
